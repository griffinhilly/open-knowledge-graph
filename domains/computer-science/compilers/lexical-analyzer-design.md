# Lexical Analyzer (Lexer) Design

## Core Idea
A lexical analyzer (lexer/scanner) is the first compilation phase that consumes raw source code and produces a token stream. It uses finite automata compiled from regular expressions to recognize lexemes, manages input buffering for efficiency, and handles special cases like comments and whitespace. Modern lexers are typically generated by tools like Lex/Flex from declarative specifications.

## Explainer

You already know that source code can be broken into tokens — identifiers, keywords, literals, operators — and that deterministic finite automata (DFAs) can recognize patterns defined by regular expressions. A **lexical analyzer** is the engineered system that puts these two ideas together at production scale: it reads raw characters from a source file and emits a stream of classified tokens that the parser can consume.

The core design follows a straightforward pipeline. First, each token category (integer literal, string literal, identifier, each keyword, each operator) is described by a regular expression. These regular expressions are compiled — usually at tool-generation time, not at runtime — into a single combined DFA. The DFA has one start state and transitions on each input character. When multiple token patterns could match at a given position, two disambiguation rules apply: **longest match** wins (so `whileTrue` is one identifier, not the keyword `while` followed by `True`), and when two patterns match the same length, **rule priority** breaks the tie (so `while` is recognized as a keyword rather than an identifier, because the keyword rule is listed first).

In practice, the lexer must handle more than just pattern matching. **Input buffering** is critical for performance — reading one character at a time from disk would be ruinously slow, so lexers use a pair of buffers (or a circular buffer) and a sentinel scheme to minimize I/O calls while still supporting the ability to "peek ahead" and "put back" characters. The lexer also silently consumes whitespace and comments (they are matched but produce no token), tracks line and column numbers for error reporting, and may handle preprocessing tasks like trigraph replacement or include-file insertion depending on the language.

Most production compilers do not hand-write their lexer. Instead, they use a **lexer generator** like Lex, Flex, or re2c. You write a specification file listing regular expressions and their associated actions (typically returning a token type and value), and the generator produces a C function containing the DFA transition table. This generated code is fast — often just an array lookup per character — and correct by construction, since the DFA faithfully implements the regular expressions. Hand-written lexers still appear in performance-critical compilers (like GCC or Clang) where the overhead of a generated table is measurable, but for most purposes, a generated lexer is the right starting point. Understanding the DFA-to-table compilation from your automata prerequisites is what lets you debug and tune these generators when token specifications produce unexpected behavior.
