# Lexical Analyzer (Lexer) Design

## Core Idea
A lexical analyzer (lexer/scanner) is the first compilation phase that consumes raw source code and produces a token stream. It uses finite automata compiled from regular expressions to recognize lexemes, manages input buffering for efficiency, and handles special cases like comments and whitespace. Modern lexers are typically generated by tools like Lex/Flex from declarative specifications.

## Questions

```yaml
- question: "A lexer specification lists 'while' as a keyword pattern and '[a-zA-Z][a-zA-Z0-9]*' as an identifier pattern (in that order). The input token is 'whileTrue'. What will the lexer produce?"
  type: multiple-choice
  options:
    - "The keyword 'while' followed by the identifier 'True'"
    - "The identifier 'whileTrue'"
    - "An error, because 'whileTrue' matches two conflicting patterns"
    - "The keyword 'while' only, consuming the first 5 characters and leaving 'True' unscanned"
  answer: 1
  explanation: "Longest match takes absolute priority over rule ordering. 'whileTrue' matches the identifier pattern with length 10, while 'while' (as a keyword) only matches with length 5. Because 10 > 5, the lexer always picks 'whileTrue' as a single identifier token — rule priority never even comes into play here. Rule priority only serves as a tiebreaker when two patterns match with equal length, which is exactly the case for input 'while' (both keyword and identifier would match 5 characters — the keyword rule wins by priority)."

- question: "When a generated lexer (produced by Lex/Flex) processes source code at compile time, when does the DFA that recognizes tokens actually get constructed?"
  type: multiple-choice
  options:
    - "At the start of each compilation run, before the first character is read"
    - "On-demand as the lexer encounters new token types for the first time"
    - "When the lexer generator is run (tool-generation time), not at compilation time"
    - "By the operating system loader when the compiler executable is loaded into memory"
  answer: 2
  explanation: "The lexer generator (Lex, Flex, re2c) processes the specification file containing regular expressions and produces C source code whose core is a precomputed DFA transition table. This compilation of regexes to DFA happens once, when you run the generator tool — not each time you compile a source file. The generated lexer contains hard-coded transition arrays; at compilation time it just executes table lookups, which is why generated lexers are so fast. This is a key design insight: the expensive NFA→DFA conversion is paid once at tool-generation time, not for every file compiled."

- question: "In lexer disambiguation, rule priority (the order patterns appear in the specification) only matters when two patterns produce a match of equal length."
  type: true-false
  answer: true
  explanation: "Longest match is always the primary rule — the lexer always selects the pattern that consumes the most characters, regardless of the order patterns are listed. Rule priority only acts as a tiebreaker when two patterns match at exactly the same length. The most important practical case is keywords vs. identifiers: the input 'while' matches both the keyword pattern (length 5) and the identifier pattern (length 5). Since lengths are equal, the keyword rule wins if listed first. Without priority, there would be no way to distinguish keywords from identifiers."

- question: "A well-designed lexer should read exactly one character at a time from disk to ensure it never reads past the end of a token."
  type: true-false
  answer: false
  explanation: "Reading one character per system call would be catastrophically slow due to operating system overhead for each I/O request. Production lexers read large blocks of characters into memory buffers (typically 4 KB or more) and scan within those buffers. The challenge this creates is that the lexer must still support lookahead — reading past a token boundary to confirm where the token ends — and then 'putting back' any characters consumed beyond the current token. Buffer schemes use sentinels and double-buffering to handle refills transparently while maintaining the illusion of character-by-character scanning."

- question: "Explain why a lexer needs lookahead, and what design problem this creates for the input buffering system."
  type: short-answer
  answer: "Many token patterns are ambiguous until a character that does not match is seen. For example, you cannot know an identifier has ended until you read the first non-identifier character. The lexer must read ahead past the token boundary to confirm it, then 'put back' the non-matching character so it can start the next token. This creates a problem for buffering: the lexer may need to look ahead across a buffer boundary. Buffer schemes handle this with paired buffers and a sentinel character at each buffer's end that signals when a reload is needed, allowing seamless lookahead without re-reading from disk."
  explanation: "Lookahead is intrinsic to lexical analysis because the DFA can only know it has finished a token when the next input character causes a transition to an error state (or no transition). The current character must then be retracted. Buffer management must support this retraction efficiently — which is why the classic two-buffer or sentinel scheme is a standard component of any production lexer implementation."
```

## Explainer

You already know that source code can be broken into tokens — identifiers, keywords, literals, operators — and that deterministic finite automata (DFAs) can recognize patterns defined by regular expressions. A **lexical analyzer** is the engineered system that puts these two ideas together at production scale: it reads raw characters from a source file and emits a stream of classified tokens that the parser can consume.

The core design follows a straightforward pipeline. First, each token category (integer literal, string literal, identifier, each keyword, each operator) is described by a regular expression. These regular expressions are compiled — usually at tool-generation time, not at runtime — into a single combined DFA. The DFA has one start state and transitions on each input character. When multiple token patterns could match at a given position, two disambiguation rules apply: **longest match** wins (so `whileTrue` is one identifier, not the keyword `while` followed by `True`), and when two patterns match the same length, **rule priority** breaks the tie (so `while` is recognized as a keyword rather than an identifier, because the keyword rule is listed first).

In practice, the lexer must handle more than just pattern matching. **Input buffering** is critical for performance — reading one character at a time from disk would be ruinously slow, so lexers use a pair of buffers (or a circular buffer) and a sentinel scheme to minimize I/O calls while still supporting the ability to "peek ahead" and "put back" characters. The lexer also silently consumes whitespace and comments (they are matched but produce no token), tracks line and column numbers for error reporting, and may handle preprocessing tasks like trigraph replacement or include-file insertion depending on the language.

Most production compilers do not hand-write their lexer. Instead, they use a **lexer generator** like Lex, Flex, or re2c. You write a specification file listing regular expressions and their associated actions (typically returning a token type and value), and the generator produces a C function containing the DFA transition table. This generated code is fast — often just an array lookup per character — and correct by construction, since the DFA faithfully implements the regular expressions. Hand-written lexers still appear in performance-critical compilers (like GCC or Clang) where the overhead of a generated table is measurable, but for most purposes, a generated lexer is the right starting point. Understanding the DFA-to-table compilation from your automata prerequisites is what lets you debug and tune these generators when token specifications produce unexpected behavior.
