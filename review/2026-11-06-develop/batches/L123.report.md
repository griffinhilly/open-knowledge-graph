## Flags

### Suspected factual errors in existing text
- peephole-optimization.md, Q0 answer and Explainer: "replaces the pair with MOV R2, R1". Dropping the STORE is wrong unless memory at [addr] is provably dead; the standard rewrite keeps the store and replaces only the load.
- peephole-optimization.md, Core Idea: "a load-then-store becomes a move" (the example is store-then-load) and "It's language and platform independent" (peephole rules are usually target-specific, as the Explainer and Q3 say).
- live-variable-analysis.md, Q3 (true-false, answer true): "An assignment to a variable that is not live ... can always be safely removed". False when the right-hand side has side effects or can fault, e.g. `x = f()` where f prints.
- lambda-calculus-foundations.md, Core Idea: "Every program in lambda calculus is a reduction sequence that simplifies expressions to normal forms." Some terms, e.g. (λx.x x)(λx.x x), have no normal form.
- lambda-calculus-foundations.md, Q1: "Variable capture" is the name of the substitution bug, not the closure scoping rule; the intended concept is free variables / lexical scope.
- lambda-calculus-foundations.md, Q3 explanation: "two expressions are equivalent if they have the same normal form (or both fail to terminate)". Non-terminating terms are not all beta-equivalent.
- lookahead-and-parsing-power.md, Explainer: "LL(1) ⊂ LL(k) ⊂ LR(1) ⊂ LR(k)". As grammar classes, LL(k) is not contained in LR(1): S → A x y | B x z, A → ε, B → ε is LL(2) but has an LR(1) reduce-reduce conflict. As language classes, LR(1) = LR(k), so the last inclusion is not strict.
- lookahead-and-parsing-power.md, Explainer: calls the common-prefix pair `A → if expr then stmt` / `A → if expr then stmt else stmt` "the classic dangling-else ambiguity". A shared prefix is a left-factoring issue; the ambiguity comes from nesting.
- ll-parsing.md, Explainer: "The standard fix is left-factoring and rewriting left recursion". Left-factoring addresses common prefixes, not left recursion.
- lr-parsing.md, Explainer: "the table was precomputed from the grammar to resolve every possible ambiguity deterministically". With the ambiguous expression grammar used in the trace, precedence declarations (not the grammar alone) resolve the conflicts.
- parser-generators.md, Core Idea: "Most real-world compilers use parser generators rather than hand-written parsers." Contradicts the file's own Explainer (GCC, Clang, Go, Rust hand-written) and is doubtful for major production compilers.
- parser-generators.md, Explainer and Q1: "A shift-reduce conflict means the grammar is ambiguous". Unambiguous grammars that are not LALR(1) also produce conflicts.
- parsing-problem-overview.md, Q3 (answer false): "An ambiguous grammar can usually be converted into an equivalent unambiguous grammar". For practical programming-language grammars this is usually possible; inherent ambiguity is rare, so "false" is doubtful with "usually".
- overload-resolution-typing.md, Core Idea: "tie-breaking by definition order". Contradicts Q0's explanation ("Declaration order is not a tiebreaker in most languages"); Java/C#/C++ do not use it.
- multi-stage-programming.md, Explainer: "template-based code generation, where errors only surface at runtime". C++ template errors surface at compile time.
- partial-evaluation-specialization.md, Q0 and Explainer: the first Futamura projection yields a compiled program; deriving a compiler is the second projection. Explainer also says binding-time analysis "ensures that specialization terminates", which BTA alone does not guarantee.
- jit-compilation.md, Q2 (true-false, true): "A JIT compiler starts by executing code in an interpreter before compiling anything". Not universal; e.g. the classic .NET CLR JIT compiled methods on first call without interpreting.
- interpreter-design-and-tradeoffs.md, Q1 explanation: bytecode "typically 10–100×" faster than tree-walking looks overstated; also Core Idea says interpreters run "without generating machine code" while listing JIT as one design.
- tree-walking-interpreters.md, Q1 explanation and Explainer: a tree-walked `3 + 4` "involves allocating node objects" at execution; AST nodes are allocated once at parse time.
- register-allocation.md, Explainer: "When a node cannot be removed ... the compiler must spill". Briggs-style optimistic coloring pushes a spill candidate and may still color it.
- reaching-definitions-analysis.md: Explainer says constant propagation needs "all reaching definitions assign the same constant", while Q4 answer says "exactly one definition". Q3 kill-set explanation says definitions "BEFORE the current block (anywhere else in the program)", which is self-contradictory; kill sets include all other definitions of the variable.
- subtyping-and-bounds.md, Q1 explanation: "anything T can do, Comparable<T> can do" is reversed. Explainer: `T super Dog` is not valid Java for a type parameter (only wildcard `? super Dog`). Explainer: unbounded T allows "you cannot call any methods" (Java allows Object methods). "making inference undecidable in the general case" is overstated.
- unification-algorithm.md, Explainer: "The classic Robinson unification algorithm runs in near-linear time with union-find". Robinson's original is exponential in the worst case; near-linear/linear algorithms are later (Huet; Martelli–Montanari; Paterson–Wegman). Also ties union-find to dynamic programming, which is not the relevant connection.
