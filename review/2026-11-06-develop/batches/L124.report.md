## Flags

### Suspected factual errors in existing text
- distributed-hash-tables.md, Q2: the keyed answer (index 1) is "The predecessor of the new node transfers the keys", but the explanation says "The successor transfers those keys to the new node". In Chord the successor hands over the keys. Option 1 is wrong, and none of the options states the correct answer. The Explainer repeats the error: "takes responsibility for the keys in its range — the predecessor transfers those keys."
- operational-transformation.md, Q4 (short-answer): this answer uses different indexing from the Explainer. It says "deletes position 2 ... to remove 'b'", then says delete(3) on "aXbc" removes 'b' and gives "aXc". The Explainer uses 0-based positions, where position 2 of "abc" is 'c' and delete(3) on "aXbc" gives "aXb". The answer is wrong under both conventions.
- logical-clocks.md, Q0: option index 1 contains leftover drafting text ("...then increments again to 7... wait, the question asks after the local event following receive.").
- logical-clocks.md, Core Idea: "enabling detection of whether one event could have influenced another". Lamport clocks cannot detect this; only vector clocks can (the file's own Q1/Q2 say so). In Q2's explanation, "Lamport timestamps can detect when events are NOT concurrent" is also mislabeled. A timestamp comparison only rules out one direction of happened-before.
- hybrid-logical-clocks.md, Core Idea: "if event A happens before event B in physical time, A's HLC is less than B's". HLC guarantees this for causal happened-before, not for physical-time order.
- eventual-consistency.md, Q4 explanation: "Real systems like Amazon DynamoDB offer configurable conflict resolution and expose vector clock information to applications". That describes the 2007 Dynamo paper, not the DynamoDB service.
- consistent-hashing.md, Explainer: "Memcached and Redis Cluster use it to distribute cache keys." Redis Cluster uses 16,384 fixed hash slots (CRC16 mod 16384), not a consistent-hashing ring. Memcached's consistent hashing lives in client libraries, not the server.
- at-least-once-semantics.md, Q0 explanation: "At-least-once queues (RabbitMQ, SQS) provide no automatic deduplication". SQS FIFO queues offer deduplication within a time window. The claim holds only for SQS standard queues.
- network-time-protocol-ntp.md, Q0: the premise says NTP slews a 500 ms offset. The reference ntpd steps the clock by default when the offset exceeds 128 ms, unless configured otherwise. A 500 ms offset would normally be stepped, not slewed.
- byzantine-fault-tolerance.md, Q0/Q4 and Explainer: n > 3f is called a bound that holds "regardless of how clever the protocol design is". That bound is for unauthenticated (oral) messages or partial synchrony. With signed messages in a synchronous model, Byzantine agreement tolerates more faults (Lamport, Shostak, Pease).
- crdts-convergent-replicated-types.md, Q0 explanation: "Last-write-wins requires coordination to determine 'last.'" LWW registers are standard CRDTs and need no coordination, only timestamps. Q3 says "CRDTs are idempotent" without qualification. That holds for state-based CRDTs. Operation-based CRDTs assume delivery without duplicates.
- multi-master-replication.md, Explainer: Google Spanner is given as an example of multi-master replication. Spanner uses Paxos groups with one leader per split for writes, so "multi-master" is a doubtful label. Q1: option 1 ("Raft requires all writes go through a single elected leader") is also a defensible answer to the question as worded.
- gossip-protocols.md, Core Idea: "database replication (Cassandra)". Cassandra uses gossip for membership and cluster state, not for replicating data. The Explainer is more accurate. Also, "information still reaches all healthy nodes" is stated as certain, but the guarantee is probabilistic.
- consistency-models.md, Explainer: quorum reads/writes are said to give linearizability. Quorum overlap alone does not make reads linearizable; a write-back or read-repair step is also needed. The definition of sequential consistency also leaves out the per-process program-order requirement.
- leader-election-algorithms.md, Explainer and Q4: "at most one leader exists at any time". Raft guarantees at most one leader per term. A deposed leader can still believe it leads for a while.
- failure-models-distributed.md, Explainer: crash failure is defined as "never recovers" and called "the most common assumption in systems like Raft and Paxos". Raft and Paxos assume crash-recovery with stable storage. The Explainer also treats "fail-stop" and crash-stop as the same, which is debatable.
- operational-transformation.md, Q3 and Explainer: OT is said to require a central server. Decentralized OT algorithms exist, though they are hard to get right. This is too strong as an absolute.
- quorum-based-replication.md, Q3 explanation: the answer is false, but the explanation opens with "so yes, it can enable faster reads", which reads as contradicting the answer.
- flp-impossibility.md, Core Idea: "sacrifice liveness (e.g., timeouts)" muddles the idea. Timeouts are a timing assumption; they are not a way of giving up liveness.
- cache-coherence-protocols.md: this is a structural issue, not a factual one. The file has two separate `## Questions` YAML blocks covering overlapping questions.
