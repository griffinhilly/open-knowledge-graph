## Flags

### Suspected factual errors in existing text

- abstract-interpretation.md, Explainer: "Astree, based on abstract interpretation with the octagon and polyhedra domains, proved the absence of runtime errors in Airbus A380 flight control software — covering 132,000 lines". As far as I know, Astrée does not use the polyhedra domain (too costly). The 132,000-line figure is usually given for the earlier A340 analysis.
- abstract-interpretation.md, Q2 short-answer explanation: "By Rice's theorem, no analysis can be both sound and complete". This needs "and always terminating" to be correct.
- bounded-model-checking.md, Q3 explanation: "K-induction is complete for finite-state systems (some k suffices)". Plain k-induction is not complete. Completeness needs extra simple-path (loop-free) constraints.
- buchi-automata-ltl-model-checking.md, Explainer: "complementing a nondeterministic Büchi automaton is expensive (doubly exponential)". Büchi complementation is singly exponential, 2^O(n log n).
- buchi-automata-ltl-model-checking.md, Q2 explanation: "GF(request -> F grant) -- every request is eventually granted". The usual formula for this is G(request -> F grant).
- buchi-automata-ltl-model-checking.md, Q4 answer: "up to 2^n states". The standard bound is 2^O(n).
- certified-compilation.md, Q3 (multiple-choice): options 0 and 3 say the same thing (both semantics are assumed or given, and only the transformation is verified). The question is ambiguous.
- certified-compilation.md, Q2 answer and Explainer: say CompCert excludes "volatile access". CompCert supports volatile. It covers most of ISO C99 rather than a "safe subset".
- certified-compilation.md, Q1 answer: "or crashes identically". CompCert's theorem gives no guarantee for source programs with undefined behavior.
- certified-compilation.md, Explainer "Beyond CompCert": "Cryptol: ... with a certified compiler to C". As far as I know, Cryptol has no certified compiler.
- certified-compilation.md, Explainer: "80-90% as fast as GCC" is unsourced. "absolute guarantee" / "absolute assurance" overstate the claim; the Explainer itself admits unverified parts.
- contract-verification-blockchain.md, Q2: the question calls total supply "immutable" (sum equals initial supply), but the answer includes mint and burn, which change supply. The Explainer says the invariant is "Σ(all balances) = initial_supply" and then says total supply is zero at deployment and grows with minting. This is self-contradictory. The Q2 explanation also calls it a "loop invariant", but it is a contract state invariant.
- contract-verification-blockchain.md, Core Idea and Explainer: lists "Formal Verification" as a company, and Q4 explanation names "Formal Verification Research". These look invented. "Runtime Verification" is a real company (Runtime Verification Inc.).
- contract-verification-blockchain.md, Explainer: "Once deployed, a contract cannot be patched". Upgradeable proxy patterns are common.
- denotational-semantics-fixed-points.md, Explainer: "any function that agrees with factorial on non-negative integers and does anything on negative integers" is a fixed point. That is false. A fixed point must satisfy g(x) = x * g(x-1) on negatives too.
- floyd-hoare-verification.md, Q3 answer: "assuming the annotations are correct". Discharged VCs establish the annotations; they are not assumed.
- floyd-hoare-verification.md, Q2 (true-false, answer true): "VC generation cannot automatically discover [invariants]". The explanation itself mentions heuristic inference tools, so the statement is arguable.
- fuzzing-formal-methods.md, Core Idea: "Spec-based fuzzing (metamorphic testing)" treats two different things as the same.
- fuzzing-formal-methods.md, Q3 answer: writes the relation as "sqrt(4*x^2) = 2*sqrt(x)". It should be 2*sqrt(x^2) = 2*abs(x), as the question says.
- fuzzing-formal-methods.md, Q3 explanation and Explainer: "Google's PageRank implementation, NVIDIA's GPU code" are unsourced claims.
- fuzzing-formal-methods.md, Q4: "symbolic execution is slow but exhaustive" and "theoretical completeness" overstate it. In hybrid fuzzing, concolic execution mainly solves branch constraints that the fuzzer cannot get past.
- fuzzing-formal-methods.md, Q5 answer: lists Scyther and ProVerif as fuzzing spec languages. They are protocol verifiers.
- fuzzing-formal-methods.md, Explainer: "QEMU-ASAN" is not a fuzzer. "Google's Continuous Fuzzing Service" is not the real name (OSS-Fuzz / ClusterFuzz). "Fuzzing has found side-channel vulnerabilities" is doubtful.
- fuzzing-formal-methods.md, Q1 explanation: the information-theory and binary-search justification is hand-waving.
- information-flow-security.md, Q1 answer: says noninterference is "composable (if A doesn't interfere with B and B doesn't interfere with C, then A doesn't interfere with C)". Noninterference is not transitive in general (hence intransitive noninterference), and it is not generally preserved under composition. The answer also says it rules out timing and memory leaks. That holds only if those are modeled as observable.
- information-flow-security.md, Q2: the chosen answer says a cryptographic hash "doesn't leak information about P". A deterministic hash does leak (equality, offline guessing).
- information-flow-security.md, Explainer: "LIO (Liquid Information Flow)". LIO stands for Labeled IO. "Android's information flow framework uses dynamic taint analysis" probably refers to the TaintDroid research system, not Android itself. The claim that dynamic monitoring knows "exactly what data actually flowed" ignores implicit flows on branches not taken.
- interactive-theorem-proving.md, Q3 explanation: "Coq's kernel is about 10,000 lines" conflicts with "a few thousand lines" elsewhere in the file. The real size is likely larger than both. "absolute certainty" (Core Idea) overstates it.
- invariant-generation.md, Q3 explanation: "If the true invariant is 'x + y <= n' ... octagon analysis can [discover it]". Octagons express ±x ± y <= c with constant c. x + y <= n has three variables, so it needs polyhedra.
- invariant-generation.md, Explainer: "Code2Inv and LoopInvGen ... use reinforcement learning or neural-guided search". LoopInvGen is data-driven enumerative/PAC learning, not neural. "lack the completeness guarantees of abstract interpretation": abstract interpretation is not complete either.
- liquid-types.md, Q1 explanation: "5 >= 0 is satisfiable". The check is validity, not satisfiability.
- liquid-types.md, Q3 explanation: the SAT/UNSAT reasoning is garbled. Rejection happens because the implication is invalid, so its negation is SAT.
- liquid-types.md, Q4: the answer says success is "the solver returns SAT". Success means the negated obligation is UNSAT. Also, the input type does not require a non-empty list, so sum [] = 0 breaks n > 0.
- liquid-types.md, Q2 explanation: says the name "liquid" means fluid. It stands for "Logically Qualified Data types".
- liquid-types.md, Explainer: "NASA/JPL verification" and "Used at companies like Google" are unsourced. It also says liquid types verify "safety and liveness properties"; liquid types target safety. "No user-written proofs" and "excludes ... induction" are outdated, since Liquid Haskell supports refinement reflection and proofs by induction. The tag "fluid-typing" follows the same misreading.
- model-checking-intro.md, Q3: the question asks why counterexamples are valuable "even when verification succeeds". No counterexample exists in that case. The explanation's attribution of the Turing Award "largely" to counterexamples is speculation.
- operational-semantics.md, Explainer: "if `e =>* v` in big-step". Big-step uses =>, not =>*.
- probabilistic-model-checking.md, Q1 explanation and Q4 explanation/Explainer: say MDP model checking is NP-hard. Max/min reachability probabilities in MDPs can be computed in polynomial time (linear programming). PCTL model checking of MDPs is polynomial in the model size.
- probabilistic-model-checking.md, Q4 answer/explanation: says nonprobabilistic model checking "typically involves NP-hard problems" and "adding randomness makes the verification problem easier". Both are false; CTL model checking is polynomial in model size.
- probabilistic-model-checking.md, Q2 answer and Explainer: say P>=0.95[φ] on an MDP means "there exists a scheduler". Standard PCTL semantics on MDPs quantify over all schedulers, so the check is min probability >= 0.95.
- probabilistic-model-checking.md, Explainer: says PRISM supports "Markov automata". Markov automata are supported by Storm, not PRISM. "thousands to tens of thousands of states" understates PRISM, which handles far larger models symbolically. "aPMC" is a tool I cannot identify. "Most formal verification assumes systems are deterministic" is false; nondeterminism is standard. The notation "P(φ ≥ 0.95)" is nonstandard (PCTL writes P>=0.95 [φ]).
- process-calculi.md, Q1 explanation: says a is "conventionally an output" and a-bar the input. Milner's convention is the reverse.
- process-calculi.md, Q3 explanation: "An external observer interacting with P can force the choice of b-or-c before a completes". The observer cannot force it. P resolves the choice internally when it takes one of its a-branches.
- process-calculi.md, Explainer: writes CCS restriction as "(new a)P". CCS notation is P\a.
- program-synthesis-formal.md, Core Idea: describes CEGIS as checking candidates "against test cases". CEGIS checks candidates with a verifier against the full specification.
- program-synthesis-formal.md, Explainer example: "bitwise AND of two integers, using only bitwise shifts and XOR". AND cannot be built from XOR and shifts, which are linear over GF(2). The example problem has no solution.
- program-synthesis-formal.md, Q4 explanation: "Myth (UC Berkeley)". Myth is from UPenn (Osera and Zdancewic), and it is type-and-example-directed rather than SMT component-based synthesis.
- program-synthesis-formal.md, Q1 explanation: calls FlashFill and "modern fuzzing harnesses" CEGIS-like. FlashFill uses version-space programming by example, not CEGIS.
- runtime-verification.md, Q4 explanation and Explainer: the Amazon and Google adoption claims are unsourced. Q5 explanation: "Java PathFinder's runtime analysis" and "coverage approaches that of systematic concurrency testing" are doubtful.
- runtime-verification.md, Q2 (true-false): "can detect all violations of safety properties ... on a single execution trace". It detects only violations that occur in the observed trace. The wording is misleading.
- sat-solving-cdcl.md, Explainer: "all learned clauses are retained" across restarts sits next to clause-database deletion in the same paragraph. The two are separate mechanisms, but the wording conflicts.
