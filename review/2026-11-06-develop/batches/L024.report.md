## Flags

### Suspected factual errors in existing text
1. authenticated-encryption.md (Explainer and Q1 explanation): "The BEAST, Lucky 13, and POODLE attacks all exploited this pattern" (padding oracle / MAC-then-encrypt). BEAST exploited predictable CBC IVs in TLS 1.0, not a padding oracle. modes-of-operation.md's own Explainer states this correctly.
2. modes-of-operation.md (Q4 explanation): "padding oracles in TLS (the BEAST and Lucky 13 attacks)". Same BEAST error; contradicts the file's Explainer.
3. blockchain-consensus-cryptography.md (Q1 answer): "recompute all subsequent hashes faster than the network (break hash collision resistance)". Recomputing hashes needs no collision; the barrier is the consensus cost. Q2 explanation also says "even if an attacker forges signatures or breaks hashing ... the high cost of PoW makes attacks prohibitively expensive", which is wrong: forged signatures enable theft without rewriting history. Q3 is a "How does..." question typed true-false.
4. code-based-cryptography.md (Core Idea): "Code-based cryptography is standardized (NIST lattice-based competition)". Misnamed; NIST's PQC process is not a lattice competition, and code-based KEMs were not among the 2024 standards. Q2 explanation: "McEliece public keys are several kilobytes" (Classic McEliece keys are hundreds of kilobytes to about 1 MB). Explainer says encryption/decryption is slow, while the Q2 explanation says it is comparable to RSA. Q1 explanation "hard average case ... easy worst-case (known codes)" is garbled. Q3 is a "Why..." question typed true-false.
5. commitment-schemes.md (Q2 explanation): hash-based commitments are "information-theoretically bound to exactly one value because the hash is deterministic". Wrong: hash commitments are computationally binding (collisions exist), as the Core Idea says.
6. computational-hardness-assumptions.md (Core Idea): "factoring implies RSA". As an assumption hierarchy (matching "DDH implies CDH"), the direction is reversed: the RSA assumption implies the factoring assumption. Explainer: one-way functions "exist if and only if P != NP for specific function families". Only OWF ⇒ P ≠ NP is known. Q2 option 1 says distinguishing is "a harder task than computing"; it is an easier task.
7. one-way-functions.md (Core Idea): "they exist if and only if P != NP for certain structured problems" (converse is open, as the file's own Q2 says). Core Idea lists digital signatures under "private-key cryptography". Q2 explanation: "OWF existence implies NP-hardness of inversion" (it implies inversion is in NP but not in P).
8. diffie-hellman-key-exchange.md (Explainer) and elliptic-curve-cryptography-basics.md (Explainer): TLS 1.3 "has removed classical DH entirely" / "uses ECDH exclusively". TLS 1.3 still defines finite-field DHE groups (RFC 7919 ffdhe groups) and PSK modes.
9. garbled-circuits.md (Core Idea): "1.5 for AND gates" contradicts the Explainer's 2 ciphertexts (half-gates). Q4 explanation: half-gates "is provably optimal: 2 ciphertexts per AND gate is the minimum". The lower bound holds only within ZRE's linear garbling model; later "three halves" garbling (2021) uses about 1.5.
10. isogeny-based-cryptography.md (Core Idea and Explainer): many problems. "SIKE/CSIDH" treated as one scheme; "NIST selected SIKE as a finalist" (SIKE was a round-3 alternate, then broken in 2022 by a classical attack); endomorphism rings "require finding lattice structures in ... dimension 1000+" (no basis); key generation via "Hilbert class polynomials" and taking "seconds to minutes" (unsupported); "codes ~1-2 KB" keys (far too small); no mention that CSIDH has a sub-exponential quantum attack. Q2 is a "Why..." question typed true-false.
11. lattice-based-cryptography.md (Q4): "All NIST post-quantum standards are based on lattice problems". SLH-DSA (FIPS 205) is hash-based. Q4 explanation calls SPHINCS+ "multivariate"; it is hash-based. Q2 explanation: ML-KEM "uses dimension n = 768 for 128-bit security" (ML-KEM-768 targets NIST category 3; ML-KEM-512 targets category 1).
12. learning-with-errors.md (Q4): Regev "ciphertext is roughly twice the size of the plaintext". A one-bit Regev ciphertext is (n+1)·log q bits, as the file's own explanation implies.
13. post-quantum-cryptography.md (Q5 and Explainer): SIKE called a "finalist". It was an alternate candidate.
14. multi-party-computation.md (Q1 answer): MPC "is exponentially slower than plaintext computation". Overhead is polynomial; the Explainer itself says 100x-1000x. The Q2 correct option says multiplication "can be performed locally" and then that it "requires interaction" (self-contradictory). Explainer: "GMW Protocol: Based on garbled circuits". GMW uses secret sharing plus OT, not garbled circuits.
15. pseudorandom-generators.md (Core Idea, Q2, Explainer): G(x) = (f(x), b(x)) with a Goldreich-Levin bit is presented as the HILL construction for any OWF. That simple construction works for one-way permutations (Blum-Micali/Yao style). HILL for general OWFs is much more involved.
16. oblivious-transfer.md: Naor-Pinkas is "based on DDH" in Q4 and "based on CDH" in the Explainer (inconsistent). Explainer: "Modern MPC systems can execute billions of OTs per second" looks overstated.
17. random-number-generation.md (Q4): /dev/random "blocks when the entropy pool is estimated to be depleted". Outdated; since Linux 5.6 (2020) /dev/random blocks only until initial seeding. Q5 explanation attributes the RSA Security $10 million report to "the Snowden leaks"; it came from Reuters reporting in 2013.
18. rsa-cryptosystem.md (Q4 explanation): doubling the modulus "roughly squares the runtime (or more)". The GNFS exponent grows by about a factor of 1.26 (plus a log factor), so attack cost goes from about 2^112 to about 2^140-2^150, not squared.
19. homomorphic-encryption.md (Q1 explanation): bootstrapping "often taking seconds per gate". Outdated for TFHE-style schemes (milliseconds per gate).
20. perfect-secrecy-and-one-time-pad.md (Q2): the correct option 2 is muddled ("some plaintexts produce the same ciphertext regardless of the key"). The explanation is right but the option text does not match it. The stem asks why the bound is "tight" but describes why it is necessary.
